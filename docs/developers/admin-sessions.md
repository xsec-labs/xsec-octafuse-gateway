# Admin browser sessions

Admin login creates a 256-bit random opaque Cookie. The database stores its SHA-256 hash, a fingerprint of the current credentials salted by the random token, and a fixed 24-hour expiry. Each browser management request checks the persisted session before injecting `MASTER_KEY`. Credential rotation invalidates existing browser sessions. Logout deletes the database record before confirming success and expiring the Cookie. External `Authorization: Bearer <MASTER_KEY>` consumers retain their current contract.

Apply migration `0017_admin_sessions.sql` using the existing D1, PostgreSQL or MySQL migration workflow before installing the Admin change. Existing browser Cookies have no session row and require login again. Proxy and billing tables retain their formats. Expired rows are removed on successful login; session credentials and raw tokens are never persisted in the table. Database/configuration errors return the existing structured 500 response and request ID.

Node requires explicit `DATABASE_URL` and existing `ADMIN_USERNAME` / `ADMIN_PASSWORD`. Cloudflare requires the actual OpenNext context, D1 `DB` binding and both credentials. `ADMIN_COOKIE_SECURE` accepts the documented boolean values; configure it for HTTPS deployments. An invalid value is a configuration error.

The public core session storage entry exports compiled JavaScript. `npm run build -w @octafuse/core` includes its compilation; Next's existing source-alias mechanism also covers this entry during Admin development. To exercise the HTTP contract, start a production Next server against a dedicated loopback PostgreSQL instance owned by `ui_validation`, apply the migrations, and set `OCTAFUSE_TEST_ADMIN_ORIGIN`, `OCTAFUSE_TEST_DATABASE_URL`, `OCTAFUSE_TEST_ADMIN_USERNAME`, `OCTAFUSE_TEST_ADMIN_PASSWORD` and `OCTAFUSE_TEST_MASTER_KEY` for that server. Run `rtk node scripts/smoke/admin-session-contract.mjs`. The contract issues real sessions and changes their expiry; use the dedicated acceptance database.

For rollback, stop Admin traffic, restore the previous source version and clear browser session Cookies. The additive session table can remain for a later forward deployment. Remove it only after all consumers of this version have stopped; remove the matching local migration ledger entry at the same time if reapplying that migration later. No business data is changed by this migration. Restoring the previous authorization implementation also restores its Cookie validation behavior, so deployment should prefer a forward fix.
